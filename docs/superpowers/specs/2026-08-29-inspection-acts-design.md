# Акты осмотра (передача / возврат) — дизайн

Дата: 2026-08-29  
Статус: одобрено в ходе обсуждения  
Бэкенд: `/Booking/{bookingId}/inspection-acts/{type}` и связанные endpoint’ы

## Проблема

Бэкенд поддерживает акты осмотра при передаче и возврате автомобиля, но на
клиенте нет Network-сервиса, ViewModel и UI для работы с ними. Пользователь не
может зафиксировать состояние автомобиля, приложить доказательства, подписать
акт или скачать его PDF.

## Цели

- Реализовать полный сценарий работы с актом осмотра на Web и Mobile.
- Поддержать оба типа актов: `Handover` и `Return`.
- Дать владельцу возможность изменять уровень топлива, пробег, комментарий
  владельца и фотографии, если это разрешено.
- Дать арендатору возможность изменять комментарий арендатора и фотографии,
  если это разрешено.
- Позволить каждой стороне подписать акт, когда это разрешает бэкенд.
- Показывать статус подписания обеими сторонами и открывать PDF после его
  появления.
- Использовать общий Network-сервис и ViewModel на всех платформах.
- Считать флаги разрешений и состояния акта в ответе бэкенда источником истины.

## Не входит в задачу

- Экраны актов для администраторов и endpoint’ы `/Admin/bookings/...`.
- Рисование подписи или биометрическая подпись на клиенте; подписание остаётся
  операцией бэкенда.
- Реализация на клиенте правил доступности бронирования.
- Офлайн-редактирование или локальная очередь загрузок.
- Отдельный глобальный список всех актов осмотра.

## Решение

**Один общий сервис `InspectionAct` и одна общая
`InspectionActViewModel`, с интерфейсами экранов для ролей на Web и Mobile.**

| Компонент | Решение |
|-------|--------|
| Выбор акта | Два действия в каждой карточке бронирования: «Акт передачи» и «Акт возврата» |
| Экран | Один экран/страница с параметрами `bookingId` и `InspectionActType` |
| Разрешения | Флаги бэкенда `canEdit*` и `canSign*` |
| Сохранение | Каждое изменение поля или фотографии сохраняется соответствующим API-вызовом |
| Источник состояния | `StateFlow` из ViewModel; бизнес-состояние не хранится в UI |
| Фотографии | Multipart-загрузка с типом `Car`, `Dashboard` или `Other` |
| PDF | Запрос download DTO у бэкенда и открытие временной ссылки |
| Платформы | Общие сервис, DTO, ViewModel и тесты; отдельные Compose UI-оболочки |

### Отклонённые варианты

- Отдельные ViewModel для Web и Mobile — дублирование бизнес-логики и обработки
  ошибок.
- Встраивание функциональности в ViewModel бронирований — сильная связь
  списков бронирований с большим независимым сценарием.
- Отображение кнопок только для захардкоженных статусов бронирования —
  дублирование правил бэкенда и скрытие уже созданных актов.

## Архитектура

```text
Карточка бронирования (Web / Mobile)
  → открыть InspectionActScreen/Page(bookingId, type)
      → InspectionActViewModel.load()
          → InspectionAct.getOrCreate / get
      → intents: изменить метрики/комментарий, загрузить/удалить фото,
        подписать, скачать
          → сервис InspectionAct
          → обновить StateFlow ответом API
```

ViewModel владеет текущим актом, состоянием загрузки, состоянием выполняемого
действия, ошибкой и результатом скачивания PDF. UI только отображает состояние
и отправляет intents. Единый ключ действия предотвращает повторные запросы для
одной и той же операции с актом.

## Network / модели

Добавить `Network/src/commonMain/kotlin/my/drivebit/network/services/InspectionAct.kt`
со следующими компонентами:

- Интерфейс и реализация `InspectionAct`.
- `InspectionActType`: `Handover`, `Return`.
- `InspectionActStatus`: `None`, `Draft`, `AwaitingOwner`,
  `AwaitingRenter`, `SignedByBoth`.
- `InspectionPhotoKind`: `Car`, `Dashboard`, `Other`.
- DTO, соответствующие бэкенду:
  - `BookingInspectionActDto`, включая nullable `photos`.
  - `BookingInspectionActPhotoDto`.
  - `BookingInspectionActDownloadDto`.
- Request-модели:
  - `UpdateInspectionMetricsRequest(fuelRemaining, mileage)`.
  - `UpdateInspectionCommentRequest(comment)`.

Сервис предоставляет операции:

- `GET` и `POST` `/Booking/{bookingId}/inspection-acts/{type}`.
- `PUT` `.../metrics` и `.../comment`.
- Multipart `POST` `.../photos`.
- `DELETE` `.../photos/{photoId}`.
- `POST` `.../sign-as-owner` и `.../sign-as-renter`.
- `GET` `.../download`.

Реализация использует авторизованный HTTP-клиент, сериализует enum-значения в
формате бэкенда и сохраняет существующие правила разбора ответов и ошибок.
Методы загрузки принимают байты, имя файла, content type и тип фотографии,
чтобы работать с файловыми picker’ами Web и Mobile.

## ViewModel

Добавить `InspectionActViewModel` и его реализацию в
`CommonViewModels/src/commonMain/kotlin/my/drivebit/viewmodels/`.

Состояние включает:

- `StateFlow<InspectionActUiState>` со значениями `Idle`, `Loading`, `Ready` и
  `Error`.
- `StateFlow<String?>` для сообщения об ошибке, видимого пользователю.
- `StateFlow<Set<InspectionActAction>>` для защиты от повторных действий.
- Состояние/effect скачивания PDF с `downloadUrl`, `fileName` и метаданными
  срока действия ссылки.

Intents включают:

- `load(bookingId, type)` и `openOrCreate(bookingId, type)`.
- `updateMetrics(fuelRemaining, mileage)`.
- `updateComment(comment)`.
- `uploadPhoto(bytes, fileName, contentType, kind)`.
- `deletePhoto(photoId)`.
- `signAsOwner()` и `signAsRenter()`.
- `downloadPdf()`.

После mutation-запросов ViewModel заменяет акт ответом API. При удалении
фотографии элемент удаляется только после успешного ответа. Пока выполняется
соответствующий запрос, действие отключено. Ошибки сохраняют последний
корректный акт и передаются через существующий механизм извлечения сообщений.

## UI

Добавить общий presentation-контракт и платформенные экраны:

- Web: `InspectionActPage`, доступная из `MyBookingsPage` и `MyDealsPage`.
- Mobile: `InspectionActScreen`, доступная из карточек поездок и входящих
  сделок.

В каждой карточке бронирования отображаются два действия:

- «Акт передачи»
- «Акт возврата»

Экран/страница акта отображает:

1. Название, номер и статус акта.
2. Поля уровня топлива и пробега, доступные при `canEditOwnerFields`.
3. Комментарии владельца и арендатора, доступные по соответствующим флагам.
4. Галерею фотографий с указанием типа и действиями загрузки/удаления.
5. Индикаторы подписания владельцем и арендатором.
6. Кнопку подписи текущей стороны, если `canSignAsOwner` или
   `canSignAsRenter` имеют значение `true`.
7. Скачивание PDF, если `hasPdf` имеет значение `true` или доступен ответ
   download-запроса.

Подписанный акт остаётся доступным в режиме только просмотра. Для загрузки,
пустой галереи, прогресса загрузки, ошибок запросов, неавторизованных ответов
и истёкших PDF-ссылок предусмотрены отдельные состояния UI.

## Обработка ошибок

- Пустой `bookingId` или недопустимый тип акта: ошибка до выполнения запроса.
- `401`: использовать существующую обработку авторизации и редирект.
- `403`: показать, что пользователь не может редактировать или подписывать акт.
- `4xx`/`5xx`/ошибка сети: сохранить последний акт и показать сообщение
  бэкенда либо локализованный fallback.
- Повторные действия загрузки, удаления и подписания игнорируются, пока уже
  выполняется такая же операция.
- PDF-ссылка считается временной; после истечения срока нужно повторно запросить
  download DTO.

## Тесты

Тесты пишутся до production-кода:

- Network-тесты проверяют каждый метод, URL, HTTP-метод, JSON-body,
  multipart-поля, enum-значения и декодирование DTO.
- ViewModel-тесты покрывают начальную загрузку, open/create, разрешения владельца
  и арендатора, обновление метрик/комментариев, загрузку/удаление фото,
  подписание, состояние PDF, защиту от повторных действий и сохранение состояния
  при ошибке.
- Web и Mobile UI-тесты проверяют обе кнопки актов, route-параметры, элементы
  по роли, подписанный акт в режиме просмотра и отображение действия PDF.
- Отдельно тестируются пути `Handover` и `Return`.
